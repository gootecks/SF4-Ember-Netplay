# M0 report: macOS Wine engine spike

## Wine boundary (issue #4)

Question: does Winsock loopback inside Wine reach native macOS processes, and does a Windows named pipe `\\.\pipe\discord-ipc-N` reach a native unix socket `$TMPDIR/discord-ipc-N`? The native helper plan assumes the first; Discord needs the second.

### Environment

| Item | Value |
| --- | --- |
| Engine | Highball `x64-sikarugir10.0_6-r22` (`wine-10.0 (Sikarugir)`, x86_64 Mach-O under Rosetta), binaries used read-only |
| Host | macOS 27.2, Apple M4 (arm64) |
| Date | 2026-10-09 |
| Prefix | throwaway `${TMPDIR}/ember-m0-loopback-<pid>`, fresh `wineboot -i`, deleted on exit; no Highball bottle or wineserver touched |
| Wine env | `DYLD_FALLBACK_LIBRARY_PATH=<engine>/lib`, `WINEDEBUG=-all`, `WINEDLLOVERRIDES=winemenubuilder.exe=d;mscoree,mshtml=`. The Highball Launcher log header sets no DYLD vars and only extra `WINEDLLPATH_PREPEND` renderer paths, which sockets do not need |
| Discord.app | not installed, so (e) tests only the Wine-side pipe namespace against a stand-in native listener |

### Method

`scripts/macos-engine/loopback/run.sh <engine-root>` builds `winsock_probe.c` (32-bit, `i686-w64-mingw32-gcc`) and runs five tests, each with bounded timeouts and unique high ports. The native side uses `nc`.

- UDP Wine to native: Wine binds `127.0.0.1:0` as GGPO does (`IrohMatchSession.cxx`), sends 5 datagrams to a native `nc -u -l`.
- UDP native to Wine: Wine binds `127.0.0.1:<port>`, native `nc -u` sends 3 datagrams and reads the replies Wine echoes back.
- TCP Wine to native: Wine connects to a native `nc -l`, sends, reads reply.
- TCP native to Wine: Wine listens, native `nc` connects, sends, reads reply.
- Discord: a native `nc -U -l $TMPDIR/discord-ipc-0` runs while Wine tries `CreateFileW` on `\\.\pipe\discord-ipc-0..9` and, if one opens, sends an IPC handshake frame.

### Results

| Test | Result | Evidence |
| --- | --- | --- |
| UDP Wine to native | PASS | `RESULT udp-wine-to-native PASS native_received_datagram_lines=1` (the 5 datagrams have no newline, so `nc` shows them as one line; Wine reported `sent=5/5`) |
| UDP native to Wine (with reply) | PASS | `RESULT udp-native-to-wine PASS received=3 replied=3`; `RESULT udp-native-to-wine-reply PASS native_got_echo_lines=3` |
| TCP Wine to native | PASS | `RESULT tcp-wine-to-native-both-ways PASS native_received=wine-hello wine_got_reply=native-pong` |
| TCP native to Wine | PASS | `RESULT tcp-native-to-wine-both-ways PASS native_got_reply=pong` |

`GetLastError=2` is `ERROR_FILE_NOT_FOUND`: Wine's pipe namespace has no `discord-ipc-N`, and Wine does not map it to `$TMPDIR/discord-ipc-N`.

### Discord log evidence (live Highball bottle, read-only)

- `sf4e-1.1.1/` contains `ember-discord.exe`, `discord_partner_sdk.dll` and `discord-build.json` (application id `1546980049692135514`, SDK `1.10.19337`).
- A case-insensitive search of `discord`, and of `presence|ember-discord|bridge|rpc|ipc`, across every log under `.../AppData/Roaming/sf4e/logs/` (launcher, sf4e, session, sidecar_bootstrap) matched nothing. Ember records no Discord helper activity there, so the logs give no evidence of whether the helper connected or failed.
- `src/discord/` shows the game-to-helper channel is a Wine-internal pipe `\\.\pipe\sf4-net-<32 hex>` (`BridgeServer`). That does not cross the Wine boundary. Only the helper's own connection to Discord (via the Partner SDK) would need the `discord-ipc-N` pipe, which the FAIL above shows is not reachable.

### Implication for M1/M2

- Winsock loopback in both directions, UDP and TCP, works. The native-helper assumption holds and no re-plan is needed for GGPO or other loopback traffic.
- Discord FAIL: a Windows process under this engine cannot reach a native Discord client. Phase I needs either a pipe-to-unix-socket bridge (a Wine-side process serving `\\.\pipe\discord-ipc-N` and relaying to `$TMPDIR/discord-ipc-N`) or degraded Discord (presence off or handled natively). Decide before M2 code depends on Discord. The stand-in listener cannot show whether a real Discord.app would accept a bridged handshake.
- Repeated under the pinned engine `ember-m0-sikarugir10.0_6-kegworks-dxvk1.10.4-moltenvk1.4.1` (built by `m0.sh engine` on an APFS sparse bundle on `/Volumes/Result`): identical results, UDP and TCP PASS both ways, Discord FAIL with `GetLastError=2` on every index. `run.sh` now also puts `<engine>/frameworks` on the dyld fallback paths, where m0.sh engines keep their dylibs.
